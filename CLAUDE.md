# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev       # Vite dev server
npm run build     # production build to dist/
npm run preview   # serve the built dist/
npm run lint      # ESLint (react-hooks + react-refresh rules)
```

There is no test runner set up yet. Plain JavaScript + JSX (no TypeScript).

Supabase credentials come from `.env.local` (git-ignored): `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY`, read in `src/lib/supabase.js`.

## Design source of truth

`design/*.dc.html` are the mockups, one per page (`Main` = Browse, `Saved`, `ForFounders`), written in a custom component format (`<x-dc>`, `<sc-for>`, `<sc-if>`, `{{bindings}}`, and a `DCLogic` class whose `renderVals()` holds the behaviour). They can't be run in this repo (they expect a `support.js` that isn't here); treat them as visual and behavioural specs. When UI is added or removed from the product, update the matching mockup too so they stay in sync.

## Architecture

- `src/App.jsx` sets up `react-router-dom`: it renders `Router` → app-wide providers → `Header` (the top bar, shared by every page) → `<main className="app-main">` → `Routes`. Because App owns `<main>`, pages must not render their own `<main>`.
- Pages live at the top of `src/`, each with its own CSS file: `Home.jsx` (`/`, Browse), `Saved.jsx` (`/saved`) and `ForFounders.jsx` (`/for-founders`, posting and editing your own listings; signed-out visitors see a "Log in to post a startup" prompt instead) and `Login.jsx` (`/login`, log in / create account). Each page renders its own `Footer`. The footer's "Submit a startup" link (and the "List your startup" button in Browse's empty state) go to `/for-founders#list`. React Router doesn't scroll to hashes, so `ForFounders` does that itself in an effect. The header uses `NavLink`, which sets `aria-current="page"` on the active nav link, and `Header.css` styles that.
- State shared between pages lives in context providers in `src/hooks/` (provider and hook in the same file, wrapped in `App.jsx`).
- `useAuth` wraps Supabase Auth (email + password). It exposes `session`, `user`, `loading` (true until the stored session is restored) and `signOut`. The header shows "Log in" or "Log out" based on `user`, and passes the current path as `state.from` so `/login` can send people back afterwards. If the Supabase project requires email confirmation, sign up shows a "Check your email" step and the confirmation link returns to `window.location.origin`. `useSaved` holds the signed-in user's saves from the Supabase `saved_listings` table (loaded with their `listings` rows embedded, newest first). It exposes `savedListings`, `savedIds` (a Set), `loading` and `toggleSaved(listing)`, which takes the whole listing so the Saved page can show it without refetching; the bookmark flips immediately and flips back if the insert/delete fails. Signed-out visitors have no saves: Browse shows the bookmark disabled and greyed out (`StartupCard` renders a disabled button when it isn't given `onToggleSave`), still with the save count, and Saved shows a "Log in to save startups" prompt.
- `Home.jsx` owns the browse-only state (search query, the hero's location text, sector/stage/size/location filters, hiring toggle, grid/list view). The hero location box matches any part of a listing's location; that box is the only location control (its suggestions are the distinct locations in the listings). The sidebar has no Location group any more, but Home keeps the `filters.locations` checklist logic (state, the `in` filter over every spelling, compared case-insensitively, and its removable tag), and `FilterSidebar`'s `CheckGroup` still supports a `limit` with "Show all", so it can be put back. Searching, filtering and sorting happen in Supabase: `listingsQuery` turns them into the `listings` request (search is `ilike` across name, sector, location and description, with the user's text escaped; ticked locations become an `in` over every stored spelling of them), and any change sends a new request (the text boxes wait for a 250ms pause). The current cards stay up, faded via `aria-busy`, until the answer arrives. Results come 12 at a time (`PAGE_SIZE`): each request is a `.range()` with `count: 'exact'`, so the first page also gives the total (shown in the toolbar). While fewer than the total are shown, a "Loading more startups…" row sits under the cards; an `IntersectionObserver` on it requests only the next 12 (from the number shown) and appends them, skipping any already shown. Re-observing after each page keeps loading while the row is still in view; after a failed page it waits for "Try again". The order ends with `id` so pages never overlap. A separate one-off request loads every listing's `sector` and `location` (`catalog`) for the sidebar counts, the location list and the hero's total, which cover all listings rather than the results. Home also builds the removable "active filter" tags. The components in `src/components/` are presentational: they get state and callbacks through props.
- Listings come from the Supabase `listings` table. `src/lib/listings.js` maps between table rows and the shape `StartupCard` renders (`fromListingRow`, `toListingRow`); optional columns can be null, so the card skips empty fields. `src/data/startups.js` only holds the filter and form option lists (`SECTORS`, `STAGES`, `SIZES`, `LOGO_COLORS`), which `FilterSidebar` imports directly.
- `StartupDialog` is the "View" popup with every field of a listing: a banner tinted with the logo colour (X at its top left), the logo overlapping it next to a Hiring/Not hiring pill, name with location and year, blurb, sector/stage/team size tiles, website and email as buttons, and the listed date and save count at the bottom. It's a native `<dialog>` opened with `showModal()`, so Esc, focus trapping and the backdrop come from the browser; a click on the backdrop also closes it. Home and Saved each keep a `viewing` startup and pass `onView` to `StartupCard`, whose name and "View" button open it. Website links are only made for http(s) addresses (https:// is added when missing).
- `StartupCard` takes a `preview` prop that renders a non-interactive copy. The For founders live preview uses it, so the preview always matches real listings.
- Sort by (`SORTS` in `src/data/startups.js`, default "Most saved"): the request orders by `created_at` desc ("Recently added", and the tiebreak for the others), `name` ("Name A–Z", using the database's collation) or `save_count` desc ("Most saved"), which sorts by each listing's `save_count` column (`saveCount` on the startup), as loaded, so cards don't jump around as you bookmark. A security-definer trigger on `saved_listings` keeps that column up to date (`supabase/newColAndTrigger.sql`, needed because `saved_listings` RLS hides other users' saves and savers don't own the listing), and column-level grants stop users writing it: only the form's columns can be inserted/updated, so **a new form field must be added to both grants there**. For the live number under the bookmark (`StartupCard`'s `saveCount` prop, shown to everyone) and in the popup, `useSaved` keeps the latest known total per listing: pages pass the listings they load to `noteSaveCounts`, this session's own saves/unsaves move it by one, and `saveCountOf(id)` reads it.
- For founders loads the signed-in user's own listings (`user_id` = their ID, newest first). With none it shows the create form; otherwise it opens the newest one in the same form for editing, with its name as the heading (a dropdown to switch between listings when there are several) and a "Create new listing" button that swaps in the create form ("Back to your listings" returns). Switching away from unsaved edits asks first. Posting inserts into `listings` (`user_id` defaults to `auth.uid()` and RLS only lets signed-in users insert their own rows) and then opens the new listing for editing; saving updates the row, and "Delete listing" (after a confirm) deletes it and opens the next listing, or the create form if none are left. Updates and deletes need the owner policies in `supabase/listings_owner_update.sql` and `supabase/listings_owner_delete.sql` (the latter also makes `saved_listings` rows cascade when their listing is deleted; `useSaved`'s `forgetListing(id)` drops it from the user's own saves). RLS doesn't error on a blocked update or delete, it just affects no rows, so the page treats "no row returned" as a failure. `toListingForm` in `src/lib/listings.js` turns a row back into the form's fields.
- Not wired up yet (same as in the mockups): the remaining `href="#"` links (footer). Listings are public as soon as they're posted; there's no review step, so don't add copy that suggests one.

## Styling conventions

- Plain CSS, one stylesheet per component, imported by that component (`Header.jsx` → `Header.css`). Page-level layout goes in the page's CSS (`Home.css`, `Saved.css`, `ForFounders.css`, `Login.css`), `App.css` only holds the app shell, and styles shared across pages (`.btn`, `.pill`) go in `index.css`. A UI piece used on more than one page becomes a component (e.g. `Switch` for the on/off toggle rows, `Field` for labelled form inputs with the `.field__input` style).
- Class names are BEM-style (`card__head`, `results__list--grid`).
- Colours, fonts and the page gutter are custom properties on `:root` in `src/index.css`. Use them rather than hard-coded hex values. Fonts (Space Grotesk for display, IBM Plex Sans for body, IBM Plex Mono for labels) are loaded from Google Fonts in `index.html` with `display=swap`. `body` sets `line-height: 1.3` (Plex's own default line height) so text keeps the same height when the web fonts swap in. Don't set `line-height: normal` anywhere, or that element will jump once the fonts load.
- Toggle and selected states are styled from ARIA attributes (`[aria-pressed='true']`, `[aria-checked='true']`, `[aria-expanded='true']`) rather than modifier classes. Keep the attribute and the style in sync.
- Responsive breakpoints: 960px (two-column layout; below it the filter sidebar collapses behind a Show/Hide toggle), 720px (hero search bar stacks), 640px (phone gutter and two-row header).
- `.container` (max-width 1280px plus the gutter) is the shared page-width wrapper.
